# Privacy

Lantern is designed for the moment when a ward's records exist only as files on a PC and in an inbox. The rule is simple: **anything derived from a file the user opens stays in the browser.** Only the bundled synthetic drill may reach the cloud.

There is **no real patient data anywhere in this repository**. The drill and the development sheets were generated by `scripts/build-drill.mjs` and are fictional: a fictional hospital, patients, hospital numbers and staff.

## What never leaves the device

- **Imported files.** They are parsed in the browser (SheetJS) and are never uploaded or synced. The same goes for their acts, candidate pairs, decisions, answers, audit trail and the worklist.

## What stays on the PC, and for how long

A ward PC is often shared, so a review of imported files must not outlive the work:
- **Saved in this browser** (IndexedDB, `src/app/store.ts`) so that work survives a closed tab, and **deleted automatically 12 hours after the last change**. Hospital IT can switch saving off entirely with the Remote Config parameter `persist_imported_reviews`: the review then lives in memory only.
- **"Finish and clear this PC"** on the worklist, and **"Delete it from this PC"** on the start page, delete every saved review in the browser. The same happens on "Start over".
- **Exports are outside Lantern's control.** A downloaded CSV or a printout carries patient names. The worklist says so next to the buttons, and the file names are marked `DRILL-` or `INCOMPLETE-`. IT can disable CSV download and printing with `allow_export`.
- Resolução do Conselho de Ministros 41/2018 asks not to keep personal data in the browser beyond the session. For a hospital deployment, add Chrome's `BrowsingDataLifetime` or ephemeral profiles, and individual logins rather than a shared one. Lantern has no authentication of its own; the initials typed on the worklist are recorded in the audit trail but prove nothing about identity.
- **Every prompt built from an imported file.** It runs on the `user-local` route (`ONLY_ON_DEVICE`) on Gemini Nano.
- **Model availability is checked before every such call.** `assertLocalReady()` requires `LanguageModel.availability()` to return `available`. This works around firebase-js-sdk issue #10635, where `ONLY_ON_DEVICE` reaches the cloud when `LanguageModel` is missing. If the model is not ready, the call is recorded as `blocked` and nothing is sent. The reviewer maps and compares by hand, and code still finds identical rows and identity problems.

## What may go to the cloud, and how that is enforced

Only content from the **bundled synthetic drill**:

1. **On a machine without Gemini Nano**, the drill's mapping and pair prompts take the SDK's `PREFER_ON_DEVICE` cloud fallback, and the ledger labels each one `in_cloud`. A mapping prompt contains the headers and up to 3 sample rows of a drill file. A pair prompt contains the clinical text of two rows.
2. **The cloud second opinion** on escalated drill pairs (`ONLY_IN_CLOUD`). It carries the clinical text, recorded times, comments and staff initials of the pair and of the patient's other rows. It carries no patient name, hospital number or bed field. In the review screen the reviewer can preview the exact text before sending, and hospital IT can switch the feature off with `cloud_second_opinion_enabled` in Remote Config.

Enforcement in the code:

| Layer | Code | Check |
|---|---|---|
| Route choice | `routeFor()` in `src/app/pipeline.ts` | `drill-hybrid` only if *every* file is cloud-eligible, otherwise `user-local` |
| Cloud payload guard | `src/ai/cloudPayload.ts` | A file is cloud-eligible only if its origin is `bundled-fixture` **and** the SHA-256 of its bytes was registered when the drill loaded. Renaming a file or editing its metadata cannot make an imported file eligible. |
| Second opinion | `askSecondOpinion()` | Calls `assertCloudAllowed(files)` before building any request |
| Last line | `runTask()` in `src/ai/models.ts` | Refuses any `cloud` call whose data origin is `user-import` |
| Tests | `tests/core/cloudPayload.test.ts` | An imported file is rejected even under a fixture's name, and so is a "fixture" whose bytes were not bundled |

## Other network traffic (no patient content)

- **App Check:** reCAPTCHA Enterprise and the App Check token exchange, only when a cloud call is made.
- **Remote Config:** the config fetch, plus Firebase Installations, which Remote Config uses.
- **Fonts:** Google Fonts (Atkinson Hyperlegible), cached by the service worker after the first visit.
- **Hosting:** responses carry `Referrer-Policy: no-referrer`.

## How to verify it yourself

1. Open **`#/lab` → S2** and run it. It runs a `user-import` prompt on the `user-local` route and reports the number of requests to Gemini endpoints (expected: 0).
2. Tick **simulate no Gemini Nano** and run S2 again. Lantern must **block** the call (no silent fallback), still with 0 requests.
3. Open DevTools → Network and filter on `firebasevertexai`. Then use **Use your own files** with any two CSV/XLSX files and compare them: no request appears.
4. The ledger shows, for every call, `inferenceSource` and the number of requests that reached `firebasevertexai.googleapis.com`, `generativelanguage.googleapis.com` or `aiplatform.googleapis.com` while it ran. The count comes from a `fetch` wrapper plus the Resource Timing API (`src/ai/netwatch.ts`).

Measured on the developer's laptop (Lab S2): 0 Gemini requests on device, and 0 requests with Gemini Nano hidden (the call was blocked). See [evaluation/gate-a-2026-11-21.md](evaluation/gate-a-2026-11-21.md).

## App Check

Firebase AI Logic is configured to require App Check. A request without a valid token is rejected with `401 Firebase App Check token is invalid`. Lantern uses `ReCaptchaEnterpriseProvider` (score-based, no checkbox) with **limited-use tokens**, so each cloud call gets a fresh token. Automatic token refresh is off, so no token is requested for on-device work or offline.

## Provider terms

The Gemini API terms say: "You may use only Paid Services when making API Clients available to users in the European Economic Area, Switzerland, or the United Kingdom." A deployment of Lantern that is reachable from those regions should therefore run its cloud path on a billing-linked Firebase project (Blaze plan).

The terms also restrict use in clinical practice. This is one more reason the cloud path accepts only bundled synthetic content. Any real deployment would need its own assessment of the provider's contract, data protection and hospital governance.

Lantern is a documentation aid for re-entry after downtime. It is not a medical device, makes no diagnosis, dosing or triage decisions, and never writes into a record system.
